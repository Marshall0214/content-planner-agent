# 实施复盘

## 实际问题与修正

1. 标准venv的ensurepip在该环境失败，改用uv建立隔离环境。首次依赖下载被网络策略阻断，按已授权安装范围重试后安装成功。
2. 沙箱默认临时目录/uv缓存不可写，影响pytest和可编辑包重装。将缓存与TMPDIR/TEMP/TMP指向项目.cache，pytest固定项目内专用目录。没有递归清理用户工作目录。
3. 首轮测试有3通过、51启动错误，主要是临时目录权限；不能将其解读为业务规则通过。修正环境后得到51通过、3失败。
4. 业务失败定位到报价JSON字典顺序：序列化按键排序，不能用values最后一项当最新报价。增加显式sequence并统一引用后，54项通过；补齐关键边界后最终65项通过。失败和成功报告均保留。
5. 补明历史报价与当前费用汇总的区别，防止保存后把旧报价I/R改写成假新报价。输入冲突证据同时保留真实提交值和原绑定值。
6. 存储层模拟“COMMIT成功但确认丢失”，检查应用没有额外查询和旧快照回写，真实已提交方案仍保留。只验证保守边界，不增加自动恢复能力。

## 范围纪律

核心闭环连同状态、费用和幂等跑通后，冻结新增能力，后续只修阻断、补边界证据和整理文档。未以第90分钟或三小时作为通过门槛。本轮总投入没有独立完整计时记录，不虚报精确开发工时。

三表足够容纳本题数据；保留逻辑状态不要求拆成更多表。报价ID引用解决参数漂移，费用身份仍按规格摘要，防止新报价造成重复收费。正常保存后终结减少无用模型调用，也让最后合法调用边界更直接。

当前完成工程和离线验证，整体P0仍缺在线证据。下一步需用户明确模型ID/端点、密钥与调用费用额度后，实际运行正常、预算反馈和工具失败/部分成功场景，核对两类真实反馈进入下一轮并驱动动作；人类审阅方案质量。资源不足或路径未取得就记录未达标，不能用离线记录补足。
